The `npx typebase-io-cli deploy` command builds your server, pushes your database schema, and deploys everything to the cloud. Typebase supports three deployment providers:

- **[Vercel](https://vercel.com/)**: serverless functions
- **[Cloudflare Workers](https://workers.cloudflare.com/)**: edge computing
- **[Deno Deploy](https://deno.com/deploy)**: edge runtime

## Quick start

Deploy to your dev environment:

```npm
npx typebase-io-cli deploy dev
```

Deploy to production:

```npm
npx typebase-io-cli deploy prod
```

The first time you run this, the CLI will ask you to:

1. **Select a deployment provider** (Vercel, Cloudflare, or Deno)
2. **Authenticate** with the provider
3. **Select or create a project** on the provider
4. **Select or create a database** on [Neon](https://neon.tech) (if your project has a database schema)

After the first deploy, the CLI remembers your choices in `typebase.json`, so future deploys are a single command.

## What happens during deploy

When you run `npx typebase-io-cli deploy`, the CLI performs these steps automatically:

1. **Regenerates the types in `_generated/`**: Runs the same logic as [`npx typebase-io-cli codegen`](/docs/cli/codegen), so you never have to run it by hand before deploying.
2. **Validates your TypeScript**: Checks your `typebase/` directory against those freshly generated types, so what gets checked is what gets built.
3. **Generates server files**: Builds the server code from your actions, schema, auth, env, and publisher config.
4. **Transpiles to JavaScript**: Converts TypeScript to JavaScript for deployment.
5. **Pushes your database schema**: Syncs your Drizzle schema to your Neon database (if applicable). In [migrations mode](/docs/database/migrations) it applies your pending migrations instead, and refuses to deploy when your schema files hold changes no migration records.
6. **Deploys the server**: Uploads the built server to your chosen provider.
7. **Sets environment variables**: Configures `DATABASE_URL` and `BETTER_AUTH_SECRET` on your provider. The key on the provider is always `DATABASE_URL`, regardless of target; each environment (`dev`, `prod`) holds its own value. Anything you declared in [`env.ts`](/docs/env) is your responsibility: set it with `npx typebase-io-cli env <target> add <KEY> <value>`, or the deployed server will refuse to boot.
8. **Saves the URL and environment variables**: Writes the deployment URL to your project-root `.env` (`TYPEBASE_APP_URL` for `prod`, `TYPEBASE_APP_URL_DEV` for `dev`), along with the connection string (`DATABASE_URL` for `prod`, `DATABASE_URL_DEV` for `dev`).

<Callout type="warn">
  Schema changes are applied (step 5) before the new server code is live (step 6), whether they arrive by push or as migrations. This is normal for
  most deployment workflows, but it means the previous version of your server briefly runs against the new schema. For destructive changes in `prod`
  (dropped columns, renamed tables), design your rollout so the old code keeps working, typically by shipping additive changes first, then removing
  the old fields in a later deploy.
</Callout>

## Options

| Argument              | Description                                            |
| --------------------- | ------------------------------------------------------ |
| `target` _(required)_ | The environment to deploy to. Must be `dev` or `prod`. |

| Flag                    | Description                                            |
| ----------------------- | ------------------------------------------------------ |
| `--provider <provider>` | Deployment provider: `vercel`, `cloudflare`, or `deno` |
| `--logs`                | Stream the server logs once the deployment is live     |

## Streaming logs after deploying

Pass `--logs` to tail the server as soon as the deployment goes live, without running a second command:

```npm
npx typebase-io-cli deploy dev --logs
```

The stream starts once the deployment URL has been printed, and keeps running until you press `x` or `Ctrl+C`. It reuses the target and provider of
the deploy, so it never asks you anything a second time. Everything else works exactly like [`typebase-io-cli logs`](/docs/cli/logs), including the
[provider differences](/docs/cli/logs#provider-differences) in delivery speed and completeness.

<Callout type="info">A failed deploy stops before the stream starts, so you never end up tailing a version that did not ship.</Callout>

## Dev vs Prod environments

Typebase supports two separate environments:

| Environment | Use case                                                  |
| ----------- | --------------------------------------------------------- |
| `dev`       | Development and testing. Uses a separate database branch. |
| `prod`      | Production. Uses the main database.                       |

Each environment gets its own:

- Deployment URL
- Database (or database branch)
- Environment variables

Deploy to dev:

```npm
npx typebase-io-cli deploy dev
```

Deploy to production:

```npm
npx typebase-io-cli deploy prod
```

## Provider setup

<Callout type="warn">
  When you log in to a provider, the CLI saves the API token it obtains (`VERCEL_TOKEN`, `CLOUDFLARE_API_TOKEN`, `DENO_DEPLOY_TOKEN`, `NEON_API_KEY`)
  to your project-root `.env`. Make sure `.env` is listed in your `.gitignore` so these tokens never end up in version control.
</Callout>

### Vercel

When you deploy to Vercel for the first time:

1. The CLI asks you to log in to Vercel (opens a browser).
2. You select an existing Vercel project or create a new one.
3. Your server is deployed as a Vercel Serverless Function using [Hono](https://hono.dev/) as the HTTP adapter.

The deployment URL looks like: `https://your-project.vercel.app`

### Cloudflare Workers

When you deploy to Cloudflare for the first time:

1. The CLI asks you to log in to Cloudflare (opens a browser).
2. You select or create a Cloudflare Worker.
3. Your server is deployed as a Cloudflare Worker.

The deployment URL looks like: `https://your-worker.your-subdomain.workers.dev`

<Callout type="info">
  Cloudflare Workers use the Fetch API natively, so environment variables are handled through Cloudflare's secrets system rather than `process.env`.
  The generated `src/env.ts` reads them from the Worker bindings, so `env` on the action context works the same as on every other provider.
</Callout>

### Deno Deploy

When you deploy to Deno Deploy for the first time:

1. The CLI asks you to log in to Deno Deploy.
2. You select or create a Deno Deploy project.
3. Your server is deployed as a Deno Deploy application.

The deployment URL looks like: `https://your-project.your-organization.deno.net`

## Database provisioning

If your project has a `db/schema.ts`, the CLI will set up a [Neon](https://neon.tech) PostgreSQL database for you:

1. **First deploy**: The CLI asks you to authenticate with Neon, then creates (or selects) a project.
2. **Schema push**: Your Drizzle schema is pushed to the database. In [migrations mode](/docs/database/migrations) your pending migrations are applied instead — see [below](#deploying-with-migrations).
3. **Environment variable**: The connection string is set on your deployment provider under the key `DATABASE_URL`, and mirrored into your project-root `.env` as `DATABASE_URL` for prod or `DATABASE_URL_DEV`.

Dev and prod deployments use separate Neon branches, so your development data doesn't affect production.

## Deploying with migrations

If your project has a `db/migrations` folder, step 2 changes: instead of pushing your schema, the CLI applies your pending migrations. Everything else is the same.

Two things behave differently from push mode:

- **Unrecorded schema changes stop the deploy.** If you edited `db/schema.ts` without running `db migrations generate`, the deploy fails and names the affected tables. Without this, migrations would apply cleanly (there are none pending), and your server would ship with types describing a column the database doesn't have — a green build where every action touching that column fails at runtime.
- **A failed migration aborts the deploy.** The server is never deployed against a database that didn't get the schema it expects.

<Callout type="warn">
  Migrations are applied **before** the new server ships, so for a few seconds your old server runs against the new schema. Adding a table or a
  nullable column is safe. Dropping a column, renaming one, or adding a `NOT NULL` constraint will break the running server until the new one takes
  over. For those, deploy in two steps: ship a migration the old server can tolerate, then remove the old shape in a follow-up deploy.
</Callout>

## Specifying the provider

You can skip the interactive prompt by passing the `--provider` flag:

```npm
npx typebase-io-cli deploy dev --provider vercel
```

```npm
npx typebase-io-cli deploy dev --provider cloudflare
```

```npm
npx typebase-io-cli deploy dev --provider deno
```

Or set the provider in `typebase.json` so it's always used:

```json title="typebase.json"
{
  "serverProvider": "vercel"
}
```

## After deploying

After a successful deploy, the CLI prints the deployment URL:

```
Deployment URL: https://your-project.vercel.app
```

This URL is also saved to your `.env` file. The key depends on the target (`TYPEBASE_APP_URL` for `prod`, `TYPEBASE_APP_URL_DEV` for `dev`) so both can coexist:

```
TYPEBASE_APP_URL=https://your-project.vercel.app
TYPEBASE_APP_URL_DEV=https://your-project-dev.vercel.app
```

Use this URL when setting up your [client](/docs/integrations/nextjs).

## Managing environment variables

Use the `npx typebase-io-cli env` command to manage environment variables on your deployment provider.

Add a variable:

```npm
npx typebase-io-cli env dev add MY_KEY my-value
```

Get a variable:

```npm
npx typebase-io-cli env dev get MY_KEY
```

See the [env command](/docs/cli/env) for more details.
