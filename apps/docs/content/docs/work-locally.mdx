---
title: Work Locally
description: Run your Typebase server on your own machine during development.
---

There are two ways to work on your backend. You can deploy to `dev` once, point your frontend at the deployed URL, and redeploy whenever the backend
changes. Or you can run the server on your own machine, where saving a file is all it takes for the running server to be the one you just wrote.

The second is a **local run**:

```npm
npx typebase-io-cli start
```

## Which one should you use?

Deploying to `dev` is less to run and a good fit while your work is mostly on the frontend, or when your backend changes once a day rather than once a
minute.

Reach for a local run when:

- **You are iterating on server code.** A save rebuilds, re-applies your schema, and restarts the server, so there is no redeploy between writing an
  action and calling it.
- **You want a debugger.** It is a Node process on your machine, so `--command "node --inspect src/index.ts"` attaches one.
- **You are offline, or the network is slow.** Nothing is uploaded and nothing is fetched from a provider.
- **You do not want to touch a shared database.** A local run defaults to a Postgres you run yourself rather than your dev branch.

<Callout type="info">
  A local run never deploys. It does not pick a provider, upload anything, write provider environment variables, or provision a database. It connects
  to the database you give it and runs the server on your machine.
</Callout>

## Starting a local run

Run it from your project root. There is no directory to change into and nothing to install first:

```npm
npx typebase-io-cli start
```

Each pass builds your server, installs its dependencies, brings your database in step with your schema, and starts it. Then it watches `typebase/` and
does all four again on every change. Press `x` or Ctrl+C to stop, and the server stops with it.

The generated server is built into a [server cache](/docs/cli/start#the-server-cache) outside your project, so a local run never adds a file for you to
review, commit, or ignore. `typebase/_server/` is left alone.

Restarting the command redoes everything, which is the way out of any state you do not trust. The [`start` reference](/docs/cli/start) covers every
option.

## Giving it a database

A local run applies your schema changes, so a project with a `db/schema.ts` has to say which database to apply them to. Set `DATABASE_URL_LOCAL` to a
Postgres you run yourself:

```bash title=".env"
DATABASE_URL_LOCAL=postgres://localhost:5432/mydb
```

That is the default because a local run pushes schema changes, and defaulting to your dev branch would push them somewhere your team shares. To reach a
[target](/docs/database/push#dev-and-prod-are-separate-branches) instead, say so:

```npm
npx typebase-io-cli start --dev-database
```

| Flag                   | Database                                         |
| ---------------------- | ------------------------------------------------ |
| none                   | `DATABASE_URL_LOCAL` in your project-root `.env` |
| `--database-url <url>` | The connection string you pass                   |
| `--dev-database`       | `DATABASE_URL_DEV`, your dev branch              |
| `--prod-database`      | `DATABASE_URL`, your production branch           |

Each one reads exactly one key, and none falls back to another. The run names the one it picked before it touches it:

```
ℹ Using the database from DATABASE_URL_LOCAL.
```

If the key you chose is empty, the run stops and tells you which one to set. A project with no `db/schema.ts` skips all of this and needs no database at
all.

## Editing your schema

Every pass brings the database in step before the server restarts, so the server you are talking to matches the schema you just saved. In [push
mode](/docs/database/push) it pushes; in [migrations mode](/docs/database/migrations) it applies your pending migrations.

Two things differ from a deploy, both because a watch loop cannot stop and wait:

- **[Drift](/docs/database/migrations#unrecorded-changes) warns instead of refusing.** A schema edit you have not recorded as a migration keeps the loop
  running, so you can carry on deciding what the migration should say. `deploy` still refuses, which is right for production.
- **The database is only touched when `typebase/db/` changed.** Editing an action rebuilds and restarts without opening a connection.

A destructive change still stops and asks, on every pass. `--skip-schema-changes-confirmation` answers in advance.

## Pointing your frontend at it

Every run writes the URL it is listening on to your project-root `.env`:

```bash title=".env"
TYPEBASE_APP_URL_LOCAL=http://127.0.0.1:8080
```

Nothing reads that key on its own. Typebase has no URL-from-environment resolution, so you write the URL into your own client, and you pick the order.
Putting the local key first means a local run wins whenever one is going, with dev and prod behind it:

```ts title="lib/typebase/client.ts"
export const client = createRouterClient<Router>({
  url: process.env.TYPEBASE_APP_URL_LOCAL || process.env.TYPEBASE_APP_URL_DEV || process.env.TYPEBASE_APP_URL || '',
});
```

Delete the line from `.env`, or comment it out, and you are back on dev without touching the client.

Browser code cannot read those directly. It needs whatever prefix your framework uses for public variables, in the same order:

```bash title=".env"
NEXT_PUBLIC_TYPEBASE_APP_URL=$TYPEBASE_APP_URL_LOCAL
```

Your framework's guide has the exact form: [Next.js](/docs/integrations/nextjs#environment-variables),
[SvelteKit](/docs/integrations/sveltekit#environment-variables), [Nuxt](/docs/integrations/nuxt#environment-variables),
[Expo](/docs/integrations/expo#environment-variables).

To run two projects at once, give one of them a different port. A port already in use fails immediately and names the flag:

```npm
npx typebase-io-cli start --port 8081
```

## Auth on localhost

Add your frontend's local origin to `trustedOrigins` so the local server accepts its requests:

```ts title="typebase/auth.ts"
export const auth = defineAuth({
  trustedOrigins: ['http://localhost:3000', 'http://localhost:3001'],
  emailAndPassword: { enabled: true },
});
```

Use whatever ports your frontend and server actually run on.

The rest is handled for you. A local run generates a `BETTER_AUTH_SECRET` if your project has none and saves it where a later deploy will find it, so
running locally first does not invalidate every session afterwards. It also writes the local URL into the generated server's auth config as
[`baseURL`](/docs/auth#the-base-url), which is what lets better-auth build callbacks and email links.

## Environment variables

The server's `.env` lives in the [server cache](/docs/cli/start#the-server-cache) and is filled from your project-root `.env` on every pass. You do not
edit it and you do not copy anything across.

Only the keys the server validates are copied: `DATABASE_URL`, `BETTER_AUTH_SECRET`, and whatever you declared in [`env.ts`](/docs/env). Provider tokens
like `NEON_API_KEY` stay in your project root, where they belong to the CLI rather than the server.

So a variable the server says is missing is missing from your project root too:

```
✗ Typebase server failed to start.

  Invalid environment variables:
    RESEND_API_KEY  Required
```

Add it to your project-root `.env` and the next pass picks it up. For the two keys the CLI manages, it can fetch the value from your provider — useful on
a fresh clone:

```npm
npx typebase-io-cli env dev get DATABASE_URL
```

```npm
npx typebase-io-cli env dev get BETTER_AUTH_SECRET
```

Use `env prod get` for the prod branch. If either prints `ENCRYPTED`, that provider is hiding the raw value, so copy it from the original source: the
Neon console for `DATABASE_URL`, or your provider's dashboard for `BETTER_AUTH_SECRET`.

## When you want a server you can read

Keeping the build outside your project is what stops a local run from adding files you have to review. The cost is that the generated server is not
somewhere you can casually open.

[`generate-server`](/docs/cli/generate-server) writes one into `typebase/_server/` instead:

```npm
npx typebase-io-cli generate-server
```

Reach for it to read the generated code, to hand a build artifact to your own infrastructure, or when you need an adapter or output format a local run
would not pick. It generates and stops there, so you install and start it yourself:

```bash
cd typebase/_server
npm install
npx tsx src/index.ts
```

It also never touches a database, so a schema change still needs [`db <target> push`](/docs/cli/db#pushing-your-schema) or [`db <target>
migrate`](/docs/cli/db#applying-migrations) alongside it.

### Rebuild on every change

`--watch` rebuilds whenever a file inside `typebase/` changes:

```npm
npx typebase-io-cli generate-server --watch
```

Press `x` or Ctrl+C to stop. A build that fails, usually a type error, is printed and leaves the watcher running.

<Callout type="warn">
  Watch mode rebuilds the files in `typebase/_server/`, but the server you started from them keeps running the old code until you restart it. Adding
  [`--command`](/docs/cli/generate-server#running-the-server-on-every-rebuild) restarts it for you.
</Callout>

`generate-server --watch --command "pnpm start"` gets close to a local run, but you still install by hand, the build still lands in your project tree,
and the database is still yours to keep in step.

## Applying a schema change on its own

You do not need a server running to move a schema change into a database:

```npm
npx typebase-io-cli db dev push
```

This is what `deploy dev` runs under the hood, so your deployed server and your next deploy stay on the same schema. In migrations mode, use
`db dev migrate`. For a Postgres on your own machine, point `db local push` at it:

```npm
npx typebase-io-cli db local push --url postgres://localhost:5432/mydb
```

If a local run is already pointed at that database, it does this for you on every change. See the [db reference](/docs/cli/db) for both commands.
