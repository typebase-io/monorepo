Typebase uses [better-auth](https://www.better-auth.com/) for authentication. It supports email/password, social logins (Google, GitHub, etc.), and more, all configured through a simple TypeScript file.

The `defineAuth` function in Typebase is a thin wrapper around better-auth, so anything you can do with better-auth you can do here. If you need features not covered in these docs (plugins, advanced session config, multi-factor auth, and more), the [better-auth documentation](https://www.better-auth.com/docs) is the full reference.

<Callout type="info">
  Authentication is optional. If your project doesn't need user accounts, you can skip this entirely. Typebase works just fine without it.
</Callout>

<Callout type="warn">
  Auth requires a database. better-auth keeps users, sessions, accounts, and verifications in your schema, so a project with an `auth.ts` must also
  have a `db/schema.ts`. When `auth.ts` exists but `db/schema.ts` doesn't, `codegen`, `generate-server`, `deploy`, and `auth generate` all stop with
  an error instead of building a server whose auth could never work.
</Callout>

## Overview

Adding authentication to a Typebase project involves four steps:

1. **Create an `auth.ts` file** in your `typebase/` directory to configure authentication.
2. **Run [`npx typebase-io-cli auth generate`](/docs/cli/auth)** to add the required authentication tables to your database schema.
3. **Get the schema into your database** with [`npx typebase-io-cli db dev push`](/docs/cli/db) (or [`npx typebase-io-cli deploy dev`](/docs/cli/deploy), which does it as part of deploying). In [migrations mode](/docs/database/migrations), `auth generate` has already recorded the migration for you, so apply it with `npx typebase-io-cli db dev migrate`.
4. **Create an auth client** on the frontend to handle sign-up, sign-in, and session management.

<Callout type="info">
  The commands below target `dev` because that's where you'll iterate. Every `dev` command has a `prod` twin. Swap in `npx typebase-io-cli db prod
  push` or `npx typebase-io-cli deploy prod` when you're ready to ship. Each target uses its own Neon branch and its own provider-side environment
  variables, so dev and prod stay isolated.
</Callout>

## Step 1: Configure authentication

Create an `auth.ts` file in the root of your `typebase/` directory:

```ts title="typebase/auth.ts"
import { defineAuth } from 'typebase-io/server';

export const auth = defineAuth({
  trustedOrigins: ['http://localhost:3000'],
  emailAndPassword: {
    enabled: true,
  },
});
```

### `defineAuth` options

The `defineAuth` function accepts all [better-auth configuration options](https://www.better-auth.com/docs/concepts/auth-config) except `database` (Typebase handles that for you). Here are some common options:

| Option                     | Description                                                           |
| -------------------------- | --------------------------------------------------------------------- |
| `trustedOrigins`           | URLs allowed to make authentication requests (e.g. your frontend URL) |
| `emailAndPassword.enabled` | Enable email/password authentication                                  |
| `socialProviders`          | Configure social login providers (Google, GitHub, etc.)               |

### Social providers example

```ts title="typebase/auth.ts"
import { defineAuth } from 'typebase-io/server';

export const auth = defineAuth({
  trustedOrigins: ['http://localhost:3000'],
  emailAndPassword: {
    enabled: true,
  },
  socialProviders: {
    google: {
      clientId: process.env.GOOGLE_CLIENT_ID!,
      clientSecret: process.env.GOOGLE_CLIENT_SECRET!,
    },
    github: {
      clientId: process.env.GITHUB_CLIENT_ID!,
      clientSecret: process.env.GITHUB_CLIENT_SECRET!,
    },
  },
});
```

### Plugins

Every built-in better-auth plugin is re-exported through Typebase so you don't have to depend on `better-auth` directly. Import server plugins from `typebase-io/server/auth-plugins` and pass them to `defineAuth`:

```ts title="typebase/auth.ts"
import { defineAuth } from 'typebase-io/server';
import { admin, magicLink } from 'typebase-io/server/auth-plugins';

export const auth = defineAuth({
  trustedOrigins: ['http://localhost:3000'],
  emailAndPassword: { enabled: true },
  plugins: [
    admin(),
    magicLink({
      sendMagicLink: async ({ email, url }) => {
        // send the link via your mailer of choice
      },
    }),
  ],
});
```

Wire the matching client plugins through `typebase-io/client/auth-plugins`:

```ts title="lib/typebase/auth-client.ts"
import { createAuthClient } from 'typebase-io/client/auth/react';
import { adminClient, magicLinkClient } from 'typebase-io/client/auth-plugins';

export const authClient = createAuthClient({
  plugins: [adminClient(), magicLinkClient()],
});
```

Both paths re-export `better-auth/plugins` and `better-auth/client/plugins` directly, so every plugin documented in the [better-auth plugin reference](https://www.better-auth.com/docs/plugins/admin) is available. Plugins shipped in separate packages (for example `@better-auth/expo`) are still imported from their own package.

## Step 2: Generate auth tables

Run the `auth generate` command to automatically add the required authentication tables (`users`, `sessions`, `accounts`, `verifications`) to your database schema:

```npm
npx typebase-io-cli auth generate
```

This command does two things:

1. **Appends tables to `db/schema.ts`**: adds the `users`, `sessions`, `accounts`, and `verifications` tables.
2. **Updates `db/relations.ts`**: registers the new tables and their relationships.

<Callout type="warn">You must have a `db/schema.ts` and an `auth.ts` file before running this command.</Callout>

After running the command, your schema will include something like this:

```ts title="typebase/db/schema.ts"
// ... your existing tables ...

export const users = p.pgTable('users', {
  id: p.text('id').primaryKey(),
  name: p.text('name').notNull(),
  email: p.text('email').notNull().unique(),
  emailVerified: p.boolean('email_verified').default(false).notNull(),
  image: p.text('image'),
  createdAt: p.timestamp('created_at').defaultNow().notNull(),
  updatedAt: p
    .timestamp('updated_at')
    .defaultNow()
    .$onUpdate(() => new Date())
    .notNull(),
});

export const sessions = p.pgTable('sessions', {
  /* ... */
});
export const accounts = p.pgTable('accounts', {
  /* ... */
});
export const verifications = p.pgTable('verifications', {
  /* ... */
});
```

## Step 3: Push the schema to your database

[`npx typebase-io-cli auth generate`](/docs/cli/auth) only edits source files. It doesn't create the tables in Postgres, so get the schema into your dev database before trying to sign in:

```npm
npx typebase-io-cli db dev push
```

In [migrations mode](/docs/database/migrations), apply the migration `auth generate` recorded instead:

```npm
npx typebase-io-cli db dev migrate
```

[`npx typebase-io-cli deploy dev`](/docs/cli/deploy) does the same thing as part of deploying — a push, or your pending migrations — so if you're about to deploy you can skip the explicit step.

<Callout type="warn">
  Skipping this step is the most common cause of "auth is configured but sign-in fails". The auth client will hit your server, but the server will
  fail to read/write `users`, `sessions`, etc. because the tables don't exist yet.
</Callout>

## The base URL

better-auth needs to know the URL your server is reachable at, so it can build callback URLs, redirects, and the links it puts in emails.

Typebase fills it in for you, differently depending on where the server is going to answer from:

| Command                                        | `baseURL` written into the generated auth config                  |
| ---------------------------------------------- | ----------------------------------------------------------------- |
| [`start`](/docs/cli/start)                     | The URL the local run listens on, such as `http://127.0.0.1:8080` |
| [`deploy`](/docs/cli/deploy) to Vercel         | `{ allowedHosts: ["*.vercel.app"] }`                              |
| [`deploy`](/docs/cli/deploy) to Cloudflare     | `{ allowedHosts: ["*.workers.dev"] }`                             |
| [`deploy`](/docs/cli/deploy) to Deno Deploy    | `{ allowedHosts: ["*.deno.dev", "*.deno.net"] }`                  |
| [`generate-server`](/docs/cli/generate-server) | Nothing                                                           |

A deploy names hosts rather than a URL because the deployment URL is not known until the upload finishes; better-auth takes the URL from each incoming request and accepts it only if the host matches. A [local run](/docs/work-locally) knows its own URL up front — it picked the port — so it writes that URL directly, and `--port` moves it with you.

<Callout type="info">
  Your own `baseURL` always wins. Typebase only adds one when your `defineAuth` config does not already have the option, so a value you set is carried
  through untouched by every command.
</Callout>

### `generate-server` and the base URL warning

`generate-server` produces an artifact you host yourself, so it cannot know where that will be and writes nothing. better-auth then says so on boot:

```
WARN [Better Auth]: [better-auth] Base URL could not be determined. Please set a valid
base URL using the baseURL config option or the BETTER_AUTH_URL environment variable.
Without this, callbacks and redirects may not work correctly.
```

It's a warning, not an error, and the server starts. Sign-in and session reads over your own frontend keep working, because those carry the origin on the request. What breaks is anything better-auth has to build a URL for on its own: social provider callbacks, magic links, and email verification links.

Set `BETTER_AUTH_URL` in the generated server's `.env` to wherever it is reachable:

```bash title="typebase/_server/.env"
BETTER_AUTH_URL=http://localhost:8080
```

Or set `baseURL` in `typebase/auth.ts` if the value is the same everywhere you run that server.

<Callout type="warn">
  Do not hardcode a localhost `baseURL` in `typebase/auth.ts` to silence this. Because your own value always wins, it ships on your next deploy and
  your deployed server builds its callbacks against your laptop. `start` already sets the local URL for you, so there is nothing to hardcode.
</Callout>

## Environment variables

Typebase uses these auth-related environment variables:

| Variable             | Description                                                                                                                                               |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BETTER_AUTH_SECRET` | A secret key used to sign session tokens. If it's missing, Typebase generates it locally the first time auth setup needs it.                              |
| `BETTER_AUTH_URL`    | The URL the server is reachable at. Only needed with `generate-server`; `start` and `deploy` write a `baseURL` instead. See [the base URL](#the-base-url) |

A project with an `auth.ts` gets `BETTER_AUTH_SECRET` added to its [env schema](/docs/env) automatically, so it's validated at boot and typed as `env.BETTER_AUTH_SECRET` on the action context. You don't declare it in `env.ts` yourself.

<Callout type="info">
  `npx typebase-io-cli auth generate` may create `BETTER_AUTH_SECRET` in your project root `.env` before your first deploy. Later, `npx
  typebase-io-cli deploy` syncs that secret to your deployment provider.
</Callout>

You can also manage provider-side variables manually with the [`npx typebase-io-cli env`](/docs/cli/env) command.
